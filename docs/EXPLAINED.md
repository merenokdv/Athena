# Athena: подробные пояснения — как всё устроено

Этот документ — «перевод» отчёта `REPORT.md` на понятный язык.  
Здесь объясняется **как работает система**, **зачем каждый шаг**, и что значат все термины.

Если коротко: **Athena** — локальный помощник, который отвечает на вопросы **только по вашим заметкам**, показывает **откуда взял ответ** и **не отправляет данные в интернет**.

Базовый отчёт для защиты: [`REPORT.md`](REPORT.md)  
Схема пайплайна: [`ARCHITECTURE.md`](ARCHITECTURE.md)

---

## 1. Что такое Athena и зачем она нужна

### Обычная проблема

У вас сотни (или тысячи) заметок в Obsidian / папке на диске. Когда нужно вспомнить «как я деплоил Next.js» или «что писал про VPN», приходится вручную открывать файлы, искать по имени, листать конспекты. Это долго.

### Что делает Athena

Вы задаёте вопрос обычным языком (как в чате). Система:

1. **ищет** в вашей базе знаний самые подходящие фрагменты;
2. **передаёт** их большой языковой модели (Qwen);
3. модель **формулирует ответ** строго по найденному;
4. в интерфейсе видны **источники** (имена заметок).

Если в заметках ничего подходящего нет — Athena должна **отказаться**, а не выдумывать.

### Чем это не ChatGPT

| ChatGPT / облачный чат | Athena |
|------------------------|--------|
| Знания из обучения модели + (иногда) поиск в сети | Знания **только из вашей папки заметок** |
| Данные уходят на серверы провайдера | Всё крутится **на вашем ПК** |
| Источник ответа часто неочевиден | В ответе есть **имя файла-заметки** |
| Может «придумать» факты | Промпт запрещает отвечать без контекста из базы |

## 2. Главная идея: RAG (поиск + генерация)

**RAG** расшифровывается как *Retrieval-Augmented Generation* — «генерация, усиленная поиском».

Без RAG модель отвечает «из головы» (из того, чему её учили).  
С RAG модель сначала получает **контекст из вашей базы**, и только потом пишет ответ.

Простая аналогия:

> Представьте экзамен.  
> «Голый» чат — студент отвечает по памяти.  
> RAG — студенту разрешили открыть **только свои конспекты**, найти нужные страницы и ответить **по ним**.

Поэтому в отчёте пайплайн записан так:

```text
ingest → embeddings → Chroma → retrieve → Qwen → UI
```

Разберём каждый этап ниже.

## 3. Пайплайн целиком (жизненный цикл)

Система живёт в двух режимах: **подготовка базы** и **ответ на вопрос**.

### Режим A. Подготовка (делается редко, после изменений заметок)

```text
Папка заметок (ATHENA_KB)
        │
        ▼
   Load — собрать .md / .txt
        │
        ▼
   Chunk — нарезать на куски ~900 символов
        │
        ▼
   Embed — превратить куски в числовые векторы
        │
        ▼
   Store — сохранить в Chroma (векторный индекс)
```

Это называется **ingest** / **индексация**. Пока индекс не пересобран, новые заметки «невидимы» для поиска.

### Режим B. Вопрос пользователя (каждый раз в UI)

```text
Вопрос в браузере
        │
        ▼
   Retrieve — найти top-k похожих кусков (+ буст по имени файла)
        │
        ▼
   Generate — Qwen пишет ответ по этим кускам
        │
        ▼
   UI показывает ответ + источники
```

## 4. Разбор этапов простыми словами

### 4.1. База знаний (Knowledge Base, БЗ, vault)

**База знаний** — папка с вашими заметками.  
В проекте путь задаётся переменной окружения `ATHENA_KB` или берётся демо-папка `knowledge_base/`.

**Vault** — привычное слово у пользователей Obsidian: «хранилище» всех заметок.

Что берём в индекс:

- `.md` (Markdown) — обычный текстовый формат заметок;
- `.txt` — простой текст;
- PDF — **не напрямую**, а после конвертации в `.md` скриптом `pdf_to_md.py`.

Что не берём:

- картинки, `assets`, папку `.git`;
- пустые файлы;
- «сырые» PDF (дают шум при поиске).

### 4.2. Ingest / индексация

**Индексация** — не «сделать оглавление как в книге», а превратить документы в форму, удобную для **смыслового** поиска компьютером.

Шаги:

1. **Load (загрузка)** — программа обходит папку и читает подходящие файлы.
2. **Chunk (нарезка)** — длинный текст режется на куски.  
   Почему: модель и поиск плохо работают с огромным файлом целиком; маленький релевантный кусок точнее попадает в ответ.
3. **Embed (эмбеддинг)** — каждый кусок превращается в вектор чисел, отражающий **смысл** текста.
4. **Store (сохранение)** — векторы кладутся в **Chroma** (локальная векторная база).

Параметры в проекте:

| Параметр | Значение | Смысл |
|----------|----------|-------|
| chunk size | ~900 символов | размер одного куска |
| overlap | 150 | «нахлёст» соседних кусков, чтобы мысль на границе не обрезалась |
| коллекция | `personal_notes_kb` | имя «полки» внутри Chroma |

Команда пересборки:

```bash
PYTHONPATH=. python -m app.ingest
```

### 4.3. Embeddings (эмбеддинги) и модель `nomic-embed-text`

**Embedding** — числовой «отпечаток смысла» текста.  
Похожие по смыслу фразы получают близкие векторы (даже если слова разные).

Пример идеи (упрощённо):

- «как задеплоить Next.js» ≈ «выкладка Next на сервер»  
- далеко от «рецепт борща»

`nomic-embed-text` — отдельная **маленькая** модель специально для таких векторов.  
Она **не** пишет ответы; она только «кодирует» текст для поиска.

### 4.4. Chroma — векторный индекс / векторная БД

**Chroma** — локальная база, которая умеет хранить векторы и быстро находить «ближайшие» к запросу.

**Векторный индекс** — структура данных «текст → вектор + метаданные (путь файла)».  
Когда вы спрашиваете, вопрос тоже превращается в вектор, и Chroma ищет куски с самым похожим вектором.

Сейчас в индексе (по отчёту):

- **956** файлов;
- **3003** чанка;
- покрытие **100%** (все подходящие файлы попали в индекс; 4 пустых пропущены осознанно).

Проверка без чтения содержимого заметок:

```bash
PYTHONPATH=. python scripts/check_index.py
```

### 4.5. Retrieve — поиск релевантных кусков

**Retrieve (ретрив)** — этап «найти, что подсунуть модели».

В Athena поиск **гибридный** (hybrid retrieve):

1. **Semantic search (семантический поиск)** — по смыслу через векторы.
2. **Поиск по ключевым словам** вопроса — дополнительный сигнал.
3. **Filename boost** — если имя файла совпадает с темой вопроса, такой кусок поднимается выше.  
   Пример: заметка `Фильмы.md` лучше находится на запрос «какие фильмы», даже если semantic search «слабо» связал короткую фразу с содержимым.
4. **Стемминг (RU)** — учёт форм слова: *фильм / фильмы / фильмов* считаются одной темой.
5. **Top-k = 4** — в промпт модели попадают **4 лучших** фрагмента (не вся база).

Почему не всю базу сразу? Потому что у модели ограничено **окно контекста** (`num_ctx`), и лишний шум ухудшает ответ.

### 4.6. Generate — генерация ответа (Qwen через Ollama)

**Generate** — модель пишет человеческий ответ.

**LLM (Large Language Model)** — большая языковая модель. Здесь: семейство **Qwen**.

**Ollama** — программа на вашем компьютере, которая запускает LLM локально (как «локальный сервер моделей»).

Варианты модели в проекте:

| Модель | Зачем |
|--------|-------|
| `qwen3.5:27b` | лучше качество (режим демо) |
| `qwen3.5:9b` | быстрее, меньше видеопамяти |
| `nomic-embed-text` | только эмбеддинги для поиска |

Числа `27b` / `9b` — примерно **миллиарды параметров** модели (размер «мозга»). Больше — обычно умнее и тяжелее по GPU/VRAM.

Важные настройки генерации:

| Параметр | Значение | Зачем |
|----------|----------|-------|
| temperature | 0.2 | меньше «креатива» и выдумок |
| num_ctx | 4096 | сколько токенов контекста держим в уме |
| thinking / think | выключен | у Qwen3 режим «размышления» иначе тормозит даже «привет» |
| system prompt | жёсткие правила | отвечать только по контексту, иначе отказать, указать источники |

**Приветствия** (`привет`, `hello` и т.п.) обрабатываются **без RAG** — мгновенно, без поиска по базе.

### 4.7. UI — интерфейс Athena

**UI (User Interface)** — то, что вы видите в браузере.

Сначала прототип мог бы быть на Gradio (быстрые демо-интерфейсы для ML).  
Сейчас — **свой минималистичный UI** на:

- **FastAPI** — веб-сервер на Python (отдаёт страницу и API);
- **static HTML/CSS/JS** — фронтенд без тяжёлого фреймворка.

Эндпоинты (адреса API):

| Метод и путь | Назначение |
|--------------|------------|
| `GET /` | открыть интерфейс |
| `GET /api/health` | жива ли модель / статус |
| `POST /api/ask` | отправить вопрос, получить `{answer, sources, model}` |

Запуск:

```bash
bash scripts/run_ui.sh
# http://127.0.0.1:7860
```

`127.0.0.1` — адрес «этот же компьютер»; порт `7860` — «дверь», на которой слушает Athena.

## 5. DSS, knowledge-assistant и бизнес-смысл

**DSS** — *Decision Support System*, система поддержки принятия решений.  
Не «робот вместо человека», а помощник: быстрее найти нужные факты/регламенты/прошлый опыт.

**Knowledge-assistant / knowledge-worker assistant** — ассистент для человека, который работает со знаниями (учёба, инженерия, внутренняя поддержка).

В учебном задании это аналог **внутренней техподдержки / поиска по регламентам отдела**, только корпус (набор документов) — **личные заметки**.

Задачи ассистента в продуктовых терминах:

1. найти релевантное;
2. сжать в понятные шаги;
3. показать источник;
4. корректно отказать вне базы;
5. показать тот же пайплайн, что подойдёт корпоративному DSS.

Имя **Athena (Афина)** — богиня мудрости: метафора «начитанного советника».  
Рассматривались также Metis, Mnemosyne, Prometheus — другие греческие метафоры знания/памяти.

## 6. Требования, scope и антигаллюцинации

### Контрольные запросы

Это заранее придуманные вопросы, по которым проверяют качество:

- должны находиться нужные конспекты (Docker, Next.js deploy, VPN, БД, CI/CD, фильмы…);
- на вопрос вне базы («пароль от чужого Wi‑Fi») — **отказ**.

Критерии качества ответа:

- **полнота** — сказал ли всё важное из заметок;
- **точность** — не исказил ли факты;
- **скорость** — приемлемое время ответа;
- **источники** — видны имена заметок;
- **корректный отказ** — не выдумал, если данных нет.

### Scope (рамки)

**Scope** — что входит в задачу и что сознательно не делаем.

Можно: md/txt (+ PDF→md), локальные модели Ollama, ответы только по retrieved-контексту.  
Нельзя: ответы «из головы», картинки/assets, юридические/медицинские заключения «от себя».

### Галлюцинации

**Галлюцинация LLM** — уверенный вымышленный факт.  
Защита в Athena:

- system prompt «только по контексту»;
- в промпт попадают лишь найденные куски;
- в UI показываются источники;
- при пустом/нерелевантном контексте — отказ.

## 7. История улучшений (почему так стало лучше)

Это важно для защиты: показать **цикл улучшения**, а не разовую сборку.

### v1 — шум PDF

PDF индексировались «как есть». Semantic search иногда поднимал мусорные куски PDF вместо нужных `.md`.  
Оценка retrieval по части запросов была слабой (~2–3 из 5).

### v2 — чистый markdown + имя файла в чанке

- прямые PDF убрали;
- в каждый чанк добавили префикс вида `Заметка: <путь>`;
- индекс стал чище.

### v3 — PDF→MD + гибридный поиск

- PDF сначала конвертируют в читаемый Markdown;
- добавили hybrid retrieve (векторы + буст имени файла + стемминг).

Типичный баг до v3: заметка называется «Фильмы», а модель говорила «в базе нет» — потому что чистый semantic search плохо цеплял короткие бытовые формулировки к **имени файла**.

Шкала оценок 1–5 и таблица прогонов — в [`TEST_LOG.md`](TEST_LOG.md).

## 8. Железо, GPU и почему ответы могли быть медленными

| Компонент | Что это |
|-----------|---------|
| CPU Ryzen 7 3700X | процессор (8 ядер / 16 потоков) |
| RAM ~62 ГБ | оперативная память |
| RTX 3090 24 ГБ | видеокарта с 24 ГБ видеопамяти (VRAM) |
| Ollama | рантайм (среда запуска) локальных LLM |

**Проблема на старте:** драйвер NVIDIA не был активен → Ollama считала на CPU → очень медленно.  
**Решение:** поставили `nvidia-dkms-580-open`, GPU заработал (`nvidia-smi` видит 3090).

Дополнительно ускорили:

- `think=false` (без длинного «внутреннего монолога» Qwen3);
- keep-alive модели (чтобы не выгружалась из памяти между вопросами);
- опция переключения на `9b` для скорости.

Почему локально, а не Custom GPT: персональные заметки, контроль данных, демонстрация на своём железе.

## 9. Экономика простыми словами

Это **учебно-демонстрационный** расчёт, не бухгалтерия.

- разовые затраты на прототип (часы × ставка);
- ежемесячная поддержка (переиндексация, правки промпта);
- лицензии ≈ 0 ₽ (локальный open-source стек);
- эффект: меньше минут на поиск ответа → экономия часов → окупаемость порядка пары месяцев в персональном сценарии.

В корпоративном пилоте (целый отдел ищет регламенты) эффект обычно больше.

## 10. Пилот, риски и регламент обновления базы

**Пилот** — пробный запуск на небольшой группе, чтобы измерить пользу до «большого» внедрения.

Успех в отчёте: ≥70% ответов на 4–5 баллов, корректные отказы, нет критичных галлюцинаций.

Главный операционный риск: **устаревший индекс**.  
Индекс **сам не обновляется**. После правок заметок:

```bash
PYTHONPATH=. python -m app.ingest
PYTHONPATH=. python scripts/check_index.py
```

Для новых PDF сначала:

```bash
PYTHONPATH=. python scripts/pdf_to_md.py
PYTHONPATH=. python -m app.ingest
```

Другие риски и смягчения — в таблице §7.2 отчёта (шум поиска, галлюцинации, медленные ответы, утечка данных при public share и т.д.).

## 11. Структура проекта (что за что отвечает)

```text
rag-dss/
├── app/
│   ├── config.py       # настройки: модели, chunk, top-k, пути
│   ├── prompts.py      # system prompt и границы поведения
│   ├── ingest.py       # индексация (load → chunk → embed → store)
│   ├── rag_chain.py    # retrieve + generate
│   ├── server.py       # FastAPI: UI + API
│   └── ui.py           # alias (удобный вход) → server
├── web/                # фронтенд Athena
├── knowledge_base/     # демо-регламенты «как у отдела»
├── data/chroma/        # сам векторный индекс на диске
├── docs/               # отчёты и пояснения
├── scripts/            # вспомогательные скрипты
└── requirements.txt    # зависимости Python
```

**Стек** (набор технологий): Ollama · Chroma · LangChain · FastAPI · HTML/CSS/JS.

**LangChain** — библиотека-«клей» для сборки цепочек LLM-приложений (загрузка документов, чанкинг, связка с векторной БД и моделью).

## 12. Как объяснить на защите за 60 секунд

1. **Проблема:** долго искать по своим/корпоративным заметкам.  
2. **Решение:** Athena — локальный RAG: поиск по базе + ответ модели + источники.  
3. **Как устроено:** заметки индексируются в Chroma; вопрос → hybrid retrieve → Qwen → UI.  
4. **Отличие от ChatGPT:** данные не в облаке; отвечает только по БЗ; умеет отказывать.  
5. **Доказательство качества:** цикл v1→v3 (шум PDF → PDF→MD → hybrid search), `check_index` 100%, демо отказ/источники.

|--------|-----------|
| **RAG** | Retrieval-Augmented Generation: сначала поиск по базе, потом ответ модели по найденному |
| **Пайплайн (pipeline)** | Цепочка этапов обработки от входа до результата |
| **Ingest / индексация** | Подготовка документов: загрузка → нарезка → эмбеддинги → запись в индекс |
| **Load** | Загрузка/обход файлов из папки |
| **Chunk / чанк** | Небольшой фрагмент документа для поиска и контекста |
| **Overlap** | Нахлёст соседних чанков, чтобы не рвать мысль на границе |
| **Embedding / эмбеддинг** | Числовой вектор, кодирующий смысл текста |
| **Вектор** | Набор чисел; «близкие» векторы ≈ похожий смысл |
| **Semantic search** | Поиск по смыслу (через близость векторов), а не только по точному совпадению слов |
| **Векторная БД / векторный индекс** | Хранилище эмбеддингов с быстрым поиском ближайших |
| **Chroma** | Конкретная локальная векторная БД в этом проекте |
| **Коллекция** | Именованная «полка» внутри Chroma (`personal_notes_kb`) |
| **Retrieve / ретрив** | Этап поиска релевантных чанков под вопрос |
| **Hybrid retrieve** | Комбинация векторного поиска, ключевых слов и буста по имени файла |
| **Filename boost** | Повышение ранга чанков, если имя файла совпадает с темой вопроса |
| **Стемминг** | Сведение словоформ к основе (*фильм/фильмы/фильмов*) |
| **Top-k** | Сколько лучших фрагментов берём в промпт (здесь 4) |
| **Релевантность** | Насколько найденный фрагмент подходит к вопросу |
| **Retrieval quality** | Качество именно этапа поиска (до генерации ответа) |
| **Покрытие индекса** | Доля файлов-кандидатов, реально попавших в индекс |
| **Переиндексация** | Повторный ingest после изменения базы |

### Модели и генерация

| Термин | Пояснение |
|--------|-----------|
| **LLM** | Large Language Model — большая языковая модель |
| **Qwen** | Семейство локальных LLM (в проекте qwen3.5) |
| **27b / 9b** | Порядок размера модели в миллиардах параметров |
| **Ollama** | Локальный рантайм для запуска LLM и embed-моделей |
| **Runtime** | Среда исполнения (здесь — то, что реально запускает модель) |
| **Generate** | Этап генерации текста ответа |
| **System prompt** | Системная инструкция модели: правила поведения и границы |
| **Промпт (prompt)** | Входной текст/инструкция для модели |
| **Контекст** | Текст, который модель «видит» при ответе (система + найденные куски + вопрос) |
| **num_ctx** | Размер окна контекста (сколько токенов модель может учесть) |
| **Токен** | Кусочек текста, которым оперирует модель (не всегда = слово) |
| **Temperature** | Степень случайности ответа; низкая → более сухие и стабильные ответы |
| **Thinking / reasoning mode** | Режим «внутренних рассуждений» у части моделей; здесь выключен ради скорости |
| **Keep-alive** | Удержание модели в памяти, чтобы не грузить заново каждый раз |
| **Холодная загрузка** | Первый запуск модели после простоя — обычно самый медленный |
| **Галлюцинация** | Выдуманный факт, поданный как истина |
| **Антигаллюцинации** | Приёмы, снижающие выдумки (только контекст, отказ, источники) |
| **Источник (source)** | Имя/путь заметки, из которой взят фрагмент |
